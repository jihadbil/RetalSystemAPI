# خطة تقليص المستودع العام وتوزيع الاستعلامات على المستودعات المتخصصة

التاريخ: 2026-10-16. الحالة: نُفذت مراحل الخطة الست واجتازت الاختبارات. التفاصيل في [تقرير التنفيذ](repository-responsibility-refactor-implementation.md). تصف الأرقام في قسم الوضع الحالي الحالة قبل التنفيذ.

## 1. الهدف والوضع الحالي

يصبح المستودع العام مسؤولًا عن العمليات الأساسية على كيان واحد. يمتلك كل مستودع متخصص استعلامات مجاله: التفاصيل، البحث، الفلاتر، الصفحات، الإسقاطات، وفحوص الارتباط والتكرار.

الفحص الحالي أظهر:

- `IRepository<T>` يحتوي 22 دالة باحتساب النسخ الزائدة.
- 15 واجهة متخصصة ترث هذه الدوال، إلى جانب `IStockRepository` و`IAccountingRepository` اللذين لا يرثان المستودع العام.
- واجهات `ICategoryRepository` و`IUnitRepository` و`ITenantRepository` و`IWarehouseRepository` فارغة؛ تنفذ احتياجاتها الحالية بالدوال الموروثة.
- الخدمات تبني `Expression` و`Specification` وتحدد التتبع والإسقاطات. لذلك تتوزع معرفة شكل الاستعلام بين الخدمة وطبقة البيانات.
- الاستيراد والتصدير في `ProductExcelService` يستخدمان إسقاطات عامة وتحميل قوائم متتبعة كاملة، ويحتاجان مسار ترحيل خاصًا يحافظ على الأداء.
- توجد آليات مشتركة مهمة سبق إصلاحها: `EntityPersistence`، فلاتر السياق، التدقيق، التزامن، وسلوك التراجع في `UnitOfWork`. تبقى موحدة.

## 2. العقد النهائي للمستودع العام

تقليص `IRepository<T>` من 22 إلى **7 دوال أساسية**:

```csharp
public interface IRepository<T> where T : BaseEntity
{
    Task<T?> GetByIdAsync(Guid id, CancellationToken ct = default);
    Task<T?> GetByIdForUpdateAsync(Guid id, CancellationToken ct = default);
    Task<bool> ExistsByIdAsync(Guid id, CancellationToken ct = default);
    Task AddAsync(T entity, CancellationToken ct = default);
    Task AddRangeAsync(IEnumerable<T> entities, CancellationToken ct = default);
    void Update(T entity);
    void SoftDelete(T entity);
}
```

قرارات العقد:

- `GetByIdAsync`: قراءة دون تتبع. `GetByIdForUpdateAsync`: تحميل متتبع للتعديل. يلزم ترحيل المستهلكين صراحة؛ الدالة الحالية قد تعيد نسخة متتبعة، رغم أن تعليق الواجهة يذكر غير ذلك.
- كلا مساري القراءة يحترمان عزل المستأجر والحذف المنطقي، بما يشمل النسخ المحلية المحذوفة أثناء وحدة العمل. لا يُستبدل الإصلاح السابق باستدعاء `FindAsync` غير محمي.
- `ExistsByIdAsync` يتحقق من معرف فقط، ولا يقبل شروطًا عامة.
- الحذف النهائي لا يبقى متاحًا لكل جذر كيان. تعرضه الواجهة المتخصصة فقط عندما يحتاجه المجال، مثل حذف بند أو تفصيل. يظل تنفيذه الآمن في `EntityPersistence`.
- `SoftDelete` الأساسي يغير حالة الكيان فقط. قرار السماح بالحذف وتنسيق حذف الأبناء يبقيان ضمن حالة الاستخدام في الخدمة.
- يصبح `Repository<T>` أساسًا مجردًا `abstract` بعد انتهاء الترحيل، ويُحذف تسجيل `IRepository<>` المفتوح في DI. تتعامل الخدمات مع الواجهات المتخصصة.
- الحفظ والمعاملات في `UnitOfWork`؛ لا تضيف المستودعات المتخصصة عمليات `SaveChanges` أو `Commit` مستقلة.

## 3. ما يخرج من الواجهة العامة

| الدوال الحالية | البديل ومسؤوليته |
|---|---|
| `GetAllAsync` | قوائم مسماة داخل المستودع المتخصص: قائمة اختيار، قائمة مفلترة، أو بيانات تصدير؛ بحسب الاستخدام الفعلي |
| `GetAllTrackedAsync` | تحميل محدد للتعديل الجماعي أو الاستيراد، بمعرفات أو مفاتيح معروفة وعلى دفعات |
| `FindAsync` بنسختيها | بحث متخصص مثل `SearchAsync(ProductQuery)` أو `GetByWarehouseAsync(...)` |
| `FirstOrDefaultAsync` بنسختيها | `GetDetailsAsync(id)` أو `GetByNumberAsync(number)` أو فحص مسمى |
| `FirstOrDefaultTrackedAsync` بنسختيها | `GetDetailsForUpdateAsync(id)` أو تحميل تخصصي متتبع |
| `FindTrackedAsync` | تحميل مجموعة معروفة مثل `GetByIdsForUpdateAsync(ids)` أو تحميل أرصدة عملية معينة |
| `SelectAsync` و`SelectFirstOrDefaultAsync` | إسقاطات مسماة ذات أنواع نتائج محددة، مثل `GetLookupAsync` و`GetExportRowsAsync` |
| `ExistsAsync(Expression)` | `NameExistsAsync` أو `NumberExistsAsync` أو `HasProductReferencesAsync` |
| `CountAsync` بنسختيها | حساب داخل البحث المتخصص، أو دالة عد ذات غرض واضح إذا احتاجها مستهلك فعلي |
| `GetPagedAsync` بنسختيها | بحث وصفحات يملكهما المستودع المتخصص عبر كائن فلترة واضح |
| `HardDelete` | عمليات صريحة في المستودعات التي تحتاج حذف بنود أو تفاصيل نهائيًا |

لا يكفي نقل أسماء `FindAsync` و`SelectAsync<TResult>` نفسها إلى كل واجهة متخصصة؛ المطلوب أن يمتلك المستودع شروط مجاله وشكل البيانات التي يعيدها.

## 4. توزيع المسؤوليات على المستودعات الحالية

الأسماء التالية توضح العقود المستهدفة، وتُضبط تواقيعها وفق سجل الاستدعاءات في أول مرحلة. لا تُنشأ دالة بلا مستهلك فعلي.

| المستودع | المسؤوليات والدوال المقترحة |
|---|---|
| `ProductRepository` | `SearchAsync(ProductQuery)`، `GetDetailsAsync`، `GetDetailsForUpdateAsync`، `GetByBarcodeAsync`، `GetByIdsAsync`، `GetImportCandidatesForUpdateAsync`، `GetExportRowsAsync`؛ مع عمليات الوحدات والباركودات والصور الموجودة |
| `CategoryRepository` | التفاصيل، الجذور، الأبناء، البحث، قوائم الاختيار، تكرار الاسم ضمن نطاقه، وفحوص وجود المنتجات أو التصنيفات التابعة |
| `UnitRepository` | قوائم الاختيار، تكرار الاسم، التحميل بالأسماء للاستيراد، وفحص استخدام الوحدة |
| `BranchRepository` | التفاصيل، البحث والصفحات، الفروع المتاحة للاختيار، وفحوص الارتباط، بالإضافة إلى الهواتف |
| `TenantRepository` | البحث الإداري والصفحات، الملف التعريفي، تكرار الاسم، وفحوص التفعيل. يبقى الفرق بين الوصول الإداري والوصول للمستأجر الحالي صريحًا |
| `WarehouseRepository` | التفاصيل، البحث، `GetByBranchAsync`، `GetByTypeAsync`، وقوائم المخازن المطلوبة لإنشاء الأرصدة |
| `CustomerRepository` | البحث، التفاصيل، تحميل التعديل، فحوص الاسم/الكود/الهاتف بحسب القواعد الحالية، وكشف الحساب والرصيد السابق الموجودة حاليًا |
| `SupplierRepository` | البحث، التفاصيل، تحميل التعديل، فحوص التكرار، الهواتف، وكشف الحساب والرصيد السابق |
| `SalesInvoiceRepository` | البحث بفلاتر المبيعات، التفاصيل، التحميل المتتبع، الاستعلام برقم الفاتورة، وفحوص ارتباط المنتج والعميل والمخزن |
| `SalesReturnRepository` | البحث والتفاصيل والتحميل المتتبع، الاستعلام برقم المرتجع، والمرتجعات السابقة المرتبطة بالفاتورة أو البنود |
| `PurchaseOrderRepository` | البحث حسب الفرع والمخزن والحالة، التفاصيل، التحميل المتتبع، وفحوص ارتباط الباركود والبنود |
| `PurchaseInvoiceRepository` | البحث والتفاصيل والتحميل المتتبع، الاستعلام برقم الفاتورة، بنودها وتفاصيل الاستلام، وفحوص ارتباط المورد والمنتج |
| `PurchaseReturnRepository` | البحث والتفاصيل والتحميل المتتبع، الاستعلام برقم المرتجع، وفحوص الكميات المرتجعة والارتباط بالمصدر |
| `StockTransferRepository` | البحث والتفاصيل، تحميل أمر التحويل للتعديل، البحث بالرقم، وفحوص ارتباط المنتجات والمخازن |
| `StockAdjustmentRepository` | البحث والتفاصيل، تحميل التسوية للتعديل، البحث بالرقم، وفحوص ارتباط المنتجات والمخزن |
| `StockRepository` | قراءة وصفحات المستودع والصالة، التنبيهات، تحميل أرصدة العملية دفعة واحدة، والأرصدة الصفرية التابعة لمنتج. استبدال واجهات الشروط والإسقاطات العامة الحالية تدريجيًا بعقود مسماة |
| `AccountingRepository` | الإبقاء على استعلامات الخزائن والمصروفات والحركات المخصصة، مع توحيد كائنات البحث ونتائج الصفحات. لا يُعاد وضع هذه الاستعلامات في المستودع العام |

في هذه الخطة تبقى الوحدات والباركودات والصور تحت مستودع المنتج، وتبقى المحاسبة والمخزون بواجهتيهما الحاليتين. تقسيم هذه المستودعات إلى مستودعات أصغر قرار لاحق إذا أثبت حجم الاستخدام الحاجة إليه، وليس شرطًا لتقليص المستودع العام.

## 5. حدود الخدمات والبنية المشتركة

- **الخدمة:** الصلاحيات، قواعد العمل، الحسابات، اختيار خطوات العملية، وتنسيق المعاملة عبر عدة مستودعات.
- **المستودع المتخصص:** شروط استرجاع بيانات مجاله، العلاقات المحملة، التتبع، الترتيب، التقطيع، العد، والإسقاط إلى بيانات القراءة.
- **`AppDbContext` و`AuditInterceptor`:** عزل المستأجر، الحذف المنطقي على مستوى الفلاتر، التحقق من ملكية الكتابة، والتدقيق.
- **`EntityPersistence`:** آلية تحديث وحذف مشتركة تحفظ `RowVersion` وحالة `Added` وحقول الإنشاء. لا تُنسخ إلى كل مستودع.
- **`UnitOfWork`:** حفظ جميع المستودعات على السياق نفسه، وتنسيق المعاملة والتراجع ومنع إعادة استخدام سياق فشل.
- **مساعد الاستعلام الداخلي:** يطبق ترتيبًا ثابتًا وعدًا قبل التقطيع ومرة واحدة للتقطيع. لا يختار علاقات المنتج أو فلاتر الفاتورة بدل المستودع المختص.

تتحول المواصفات الخاصة بالمجالات من `RetalSystemAPI.Services/*/Specifications` إلى تفاصيل تنفيذ داخل طبقة البيانات، أو تستبدل باستعلام مباشر هناك. لا تتعامل واجهات الخدمات مع `ISpecification` أو `Expression` أو `IQueryable`.

تنشأ كائنات بحث مثل `ProductQuery` و`SalesInvoiceQuery` تحت `RetalSystemAPI.DataAccess/Queries/<Domain>`، وأنواع نتائج القراءة تحت `QueryResults/<Domain>`. لا تعتمد طبقة البيانات على `Services.Common.PagedResult` أو DTOs واجهة HTTP؛ تحوّل الخدمة نتائج البيانات إلى DTOs الحالية.

## 6. مثال على الاستخدام بعد النقل

حاليًا:

```csharp
var spec = new ProductSummarySpec(categoryId);
var (items, totalCount) = await uow.Products.GetPagedAsync(spec, pageNumber, pageSize, ct);
```

بعد النقل:

```csharp
var page = await uow.Products.SearchAsync(
    new ProductQuery { CategoryId = categoryId, PageNumber = pageNumber, PageSize = pageSize }, ct);
```

داخل `ProductRepository` يحدد التنفيذ الفلاتر والعلاقات والإسقاط والترتيب. يمكنه استخدام مساعد تقني داخلي لتطبيق الصفحة؛ لا يفوض معرفة المنتج إلى محرك عام جديد. يستمر تحويل النتيجة إلى DTO في الخدمة.

## 7. مراحل التنفيذ

### المرحلة الأولى: تثبيت خط الأساس وحصر المستهلكين

1. تشغيل اختبارات المشروع الحالية، ومنها اختبارات SQL Server مع `RETAL_TEST_SQLSERVER`. آخر نتيجة في جلسة الإصلاح كانت 51 اختبارًا ناجحًا؛ يُعاد تثبيت الخط الأساس عند بدء التنفيذ.
2. إعداد سجل لكل استخدام للدوال التي ستُحذف: الخدمة والطريقة، المستودع، الفلاتر، العلاقات، حقول الإسقاط، وحاجة التتبع.
3. تمييز مسارات القراءة والتعديل التي تستخدم `GetByIdAsync` حاليًا، لأن تغيير معنى التتبع يحتاج تحديث المستهلكين.
4. تحديد الدوال الجديدة المطلوبة فعليًا؛ تجميع الاستخدامات المتشابهة دون إضافة دالة لكل سطر استعلام.

**مخرج المرحلة:** سجل نقل ومصفوفة العقود النهائية للمستودعات الخمسة عشر الموروثة، إضافة إلى مراجعة الواجهتين المستقلتين.

### المرحلة الثانية: تجهيز العقود والبنية المشتركة

1. إضافة كائنات البحث ونتائج القراءة والصفحات داخل طبقة البيانات.
2. إضافة العقود المتخصصة جنبًا إلى جنب مع القديمة بصورة مؤقتة.
3. تجهيز فصل القراءة دون تتبع عن القراءة للتعديل، مع اختبارات العزل والحذف للنسخ المحلية.
4. إبقاء مساعدي الحفظ والصفحات تقنيين داخليين، وعدم نقل معرفة المجال إلى `BaseRepository` بديل.

**مخرج المرحلة:** عقود قابلة للبناء مع استمرار عمل المستهلكين الحاليين.

### المرحلة الثالثة: نقل الدليل والفروع

الترتيب: التصنيفات والوحدات، ثم الفروع والمخازن، ثم العملاء والموردون، ثم استعلامات المستأجرين.

لكل مجموعة: تنفيذ العقود المخصصة، نقل المواصفات، تحديث الخدمات، ثم التحقق من البحث والتفاصيل والتعديل والحذف. تُحذف الدوال الانتقالية بعد آخر مستهلك لها في المجموعة.

**مخرج المرحلة:** الواجهات الفارغة أصبحت تمتلك استعلامات فعلية، ولا تبني خدمات هذه المجالات استعلامات عامة.

### المرحلة الرابعة: المنتج والمخزون والاستيراد

1. نقل البحث والتفاصيل والبحث بالباركود والتحميل الدفعي إلى مستودع المنتج.
2. استبدال واجهات الإسقاط المفتوحة في المنتج والمخزون بنتائج محددة الغرض.
3. ترحيل `ProductExcelService` واستيراد/تصدير البيانات بصورة مستقلة؛ تحميل المفاتيح المطلوبة على دفعات مع الحفاظ على كشف التكرار وتوليد الباركود وسلوك التحديث الحالي.
4. توحيد استعلامات المخزون المخصصة للقراءة وللتعديل، والمحافظة على تطابق العد والصفحات وحذف الأرصدة الصفرية مع المنتج.

**مخرج المرحلة:** لا تستخدم خدمات المنتج والمخزون والاستيراد الدوال العامة المحذوفة، ولا تعوض التحميل الجماعي باستعلام لكل صف.

### المرحلة الخامسة: المستندات والحركات

الترتيب: طلبات وفواتير المشتريات ومرتجعاتها، ثم المبيعات ومرتجعاتها، ثم التحويلات والتسويات.

1. نقل استعلامات التفاصيل والأرقام والفلاتر والبنود والارتباطات إلى المستودع المسؤول عنها.
2. استبدال `ItemExistsAsync(Expression)` وما شابهه بدوال واضحة مثل `HasProductReferencesAsync` بحسب الاستخدام.
3. إبقاء احتساب الإجماليات والكميات والقيود المالية وقواعد الاعتماد والإلغاء في الخدمات الحالية.
4. اختبار إنشاء المستند وتعديله واعتماده وإلغائه والمرتجعات وتأثير المخزون والحسابات، مع التزامن والتراجع.

**مخرج المرحلة:** الخدمات تنسق العملية، والمستودعات تمتلك طريقة جلب بياناتها.

### المرحلة السادسة: إغلاق الواجهة العامة القديمة

1. إزالة جميع الدوال الزائدة من `IRepository<T>` و`Repository<T>`، وإبقاء الدوال السبع المحددة.
2. جعل الأساس مجردًا وحذف التسجيل العام المفتوح في `DataAccessServiceExtensions`، مع الحفاظ على تسجيل الواجهات المتخصصة ووحدة العمل.
3. إزالة المواصفات وواجهات التوافق القديمة بعد التأكد من غياب المستهلكين في جميع المشاريع والاختبارات.
4. نقل اختبارات الصفحات والبحث من المستودع العام إلى المستودعات المتخصصة. يمكن استخدام مستودع اختبار مشتق لاختبار العمليات الأساسية فقط.
5. إضافة تحقق معماري يمنع إعادة `ISpecification` و`Expression` والإسقاطات المفتوحة إلى العقد العام، ويمنع بناء مواصفات بيانات في الخدمات التي رُحلت.

**مخرج المرحلة:** لا يوجد مسار رجوع خفي للواجهة العامة الواسعة، وتعمل المجموعة كاملة بالعقود الجديدة.

## 8. شروط القبول

- المستودع العام يعرّض الدوال السبع فقط؛ لا بحث عام أو صفحات أو عد مفلتر أو إسقاطات مفتوحة أو حذف نهائي عام.
- كل استعلام مجال له عقد مسمى ومالك محدد؛ استدعاء مستودع متخصص لا ينتهي بمجرد تغليف `base.FindAsync` أو `base.GetPagedAsync`.
- الخدمات المرحّلة لا تبني شروط قاعدة البيانات أو التضمينات أو تحدد التتبع، ولا تستقبل `IQueryable`.
- استخدام مساعد مشترك محدود للترتيب والتقطيع والحفظ مقبول؛ لا تتكرر آليات الأمان والتزامن في كل مستودع.
- لا تتغير استجابات API أو قواعد العمل أو دقة الحسابات. ولا يتطلب هذا التنظيم ترحيل مخطط قاعدة البيانات ما دامت نماذج EF وتكويناتها لم تتغير.
- تجتاز اختبارات العزل والحذف المنطقي والتزامن وحالة السجل الجديد والتراجع وجميع اختبارات SQL Server الموجودة والجديدة اللازمة.
- لا تتكرر العناصر بين الصفحات ذات الترتيب نفسه، ويُحسب الإجمالي قبل التقطيع، وتطبق الصفحة مرة واحدة.
- لا يظهر N+1 في الاستيراد أو تحميل أرصدة البنود؛ تُقارن الاستعلامات وحجم البيانات على عينات ممثلة قبل النقل وبعده.

## 9. حدود النطاق

توجد ست خدمات تستخدم `AppDbContext` مباشرة: `DashboardService` و`FinancialReconciliationService` و`PosCashService` و`TenantService` و`UserService` و`AuthService`. هذا مسار منفصل عن تقليص المستودع العام؛ تُحصر قراءاتها عند التنفيذ، وتُنقل الاستعلامات المتداخلة مع المجالات الجاري تعديلها فقط إذا لزم ذلك.

فصل جميع هذه الخدمات عن السياق أو إنشاء مستودعات جديدة للتقارير ونقاط البيع والهوية يمكن تنفيذه لاحقًا بخطة مستقلة. تبقى إدارة الهوية عبر `UserManager` و`RoleManager`؛ لا تُحوّل إلى CRUD عام.

التنفيذ تدريجي حسب المجال، مع بناء واختبارات بعد كل دفعة. لا يُستبدل المستودع العام دفعة واحدة ثم تُصلح أخطاء الخدمات لاحقًا.
