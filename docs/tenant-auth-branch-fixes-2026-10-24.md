# إصلاح خدمات المستأجرين والمصادقة والفروع

## التغييرات

- يمنع حذف الفرع المرتبط بمستخدمين أو مستودعات أو معاملات، بما فيها السجلات التاريخية والمحذوفة منطقياً. تعيد الخدمة `422`، ويمكن تعطيل الفرع بدلاً من حذفه.
- تضيف الهجرة حراساً في SQL Server تمنع حذف الفرع مع وجود ارتباطات، وتمنع إضافة ارتباط إلى فرع محذوف. تعمل داخل معاملة الكتابة نفسها لحماية الفحص من الطلبات المتزامنة.
- تُحذف هواتف الفرع منطقياً معه في عملية حفظ ذرية. وتحتفظ عملية تحديث الهواتف بمعرّفات الأرقام الموجودة، وتعيد `409` لتعارضات الأرقام.
- يفرض فهرس فريد `(TenantId, Name)` فرادة أسماء الفروع غير المحذوفة. تعيد الخدمة تعارضات هذا الفهرس إلى العميل كـ`409`.
- يتحقق Identity من تعارض اسم المستخدم مع بريد أي حساب آخر والعكس، بعد التطبيع. يحجز جدول `UserLoginIdentifiers` القيم المطبّعة بقيد فريد، وتزامنه مشغّلات `AspNetUsers` داخل معاملة إنشاء/تعديل الحساب. يسمح بتساوي اسم المستخدم وبريده للحساب نفسه، ويحرر القيم عند تعديلها أو حذف الحساب.
- تُجهز بيانات استجابة تحديث الشعار وإحصائياتها قبل حفظ الرابط، فلا يسبب فشل استعلامات الاستجابة بعد الحفظ حذف الشعار المعتمد.

## تهيئة مستأجر قابل للاستخدام

المسار الجديد `POST /api/tenants/provision` يتطلب مستخدماً موثقاً بدور `SuperAdmin` وصلاحية `Tenants.Edit`. تتحقق الخدمة ومصنع نطاق التنفيذ من دور مسؤول المنصة أيضاً.

```json
{
  "tenant": {
    "name": "اسم المنشأة",
    "phoneNumber": "0912345678"
  },
  "branchName": "الفرع الرئيسي",
  "branchAddress": "العنوان",
  "adminUserName": "tenant-admin",
  "adminEmail": "admin@example.com",
  "adminPassword": "<كلمة مرور تستوفي سياسة النظام>"
}
```

تُنشأ المنشأة والفرع وحساب المسؤول، مع إسناد دور `Admin`، داخل معاملة واحدة. يجب أن يكون دور `Admin` مهيأ مسبقاً بواسطة تهيئة أدوار النظام. عند فشل التحقق من الحساب أو إسناد الدور تُلغى العملية كلها، بما فيها حجوزات معرّفات الدخول.

تحتوي استجابة `201` على `tenantId` و`branchId` و`adminUserId`. يستطيع الحساب الجديد تسجيل الدخول عبر المسار المعتاد. يستخدم التنفيذ نطاق DI منفصلاً للمستأجر الجديد ويحافظ على هوية مسؤول المنصة وسياق طلبه الأصلي.

## تطبيق الهجرة

الهجرة: `20261024071237_HardenTenantAuthAndBranchLifecycle`.

```sh
dotnet ef database update --project RetalSystemAPI.DataAccess --startup-project RetalSystemAPI
```

تستخدم أداة EF إعداد الاتصال الموثوق المعتاد. اختُبرت الهجرة على قواعد SQL Server محلية مؤقتة؛ لم تُطبّق على قاعدة تشغيل فعلية.

قبل تعديل المخطط، تتوقف الهجرة إذا وجدت أسماء فروع نشطة مكررة أو تعارضاً بين معرّفات دخول حسابات مختلفة. لا تعيد تسمية الفروع أو الحسابات تلقائياً. يمكن تحديد التعارضات بالاستعلامين التاليين، ثم معالجتها وإعادة تطبيق الهجرة:

```sql
SELECT TenantId, Name, COUNT(*) AS DuplicateCount
FROM Branches
WHERE IsDeleted = 0
GROUP BY TenantId, Name
HAVING COUNT(*) > 1;

SELECT a.Value AS LoginIdentifier, COUNT(DISTINCT u.Id) AS AccountCount
FROM AspNetUsers u
CROSS APPLY (VALUES (u.NormalizedUserName), (u.NormalizedEmail)) a(Value)
WHERE a.Value IS NOT NULL AND a.Value <> N''
GROUP BY a.Value
HAVING COUNT(DISTINCT u.Id) > 1;
```

تملأ الهجرة حجوزات الدخول للحسابات الموجودة، وتعلّم هواتف الفروع المحذوفة سابقاً بأنها محذوفة منطقياً لتحرير أرقامها.

## التحقق

تغطي `TenantAuthBranchFixTests` قيود المسار الجديد، وعزل سياق المستأجر، والتراجع عند فشل Identity وإسناد الدور، وحجوزات الدخول المتزامنة، وتعارضات أسماء الفروع وأرقامها، وحماية حذف الفرع، واتساق ملف الشعار مع قاعدة البيانات، وفحوص ترحيل البيانات القديمة.

قبل دمج أحدث تحديثات `V2`، اجتازت مجموعة الأمان والخدمات كاملة 193 اختباراً دون فشل أو تخطٍ على SQL Server 2022 محلي مؤقت، بينها 16 اختباراً لهذا الإصلاح. شمل التحقق تطبيق ملف SQL الخاص بالترقية مرتين للتأكد من قابليته لإعادة التنفيذ.

عند تجهيز الدفع، كان الفرع البعيد يحتوي 40 commit إضافية. وُفّقت إصلاحاتنا مع تلك التحديثات، وأُزيلت تعريفات مكررة وأُكملت عقود الخدمات اللازمة للبناء، مع الاحتفاظ بمعاملات Identity الذرية وميزات البحث والمجاميع المالية. نجح البناء دون تحذيرات، وأكد فحص EF تطابق النموذج مع الهجرة.

بعد الدمج، شُغّل 305 اختبارات: نجح 301 وفشل 4. صُحح اختلاف اسم جهة إصدار الفاتورة ليستخدم الاسم التجاري عند توفره، ثم نجحت إعادة تشغيل 17 اختباراً تشمل اختبارات الإصلاحات الستة واختبار جهة الإصدار، دون تخطٍ. بقيت ثلاث حالات فشل من `EngineeringAuditV2RegressionTests` المضافة ضمن تحديثات الفرع الأخرى:

- `Product_and_opening_stock_are_persisted_in_one_save`: يتوقع الاختبار حفظ المنتج ورصيده مرة واحدة، بينما التنفيذ الموجود يستدعي الحفظ عدة مرات داخل المعاملة.
- `Transfer_persists_notes_with_status_and_cancelled_transfer_cannot_move_stock`: يتوقع الاختبار تغيير الحالة عبر `UpdateAsync`، بينما التنفيذ الموجود يقصر تغييرها على مسار الاعتماد.
- `Return_rechecks_original_invoice_after_interleaved_cancellation`: يفشل سيناريو الإلغاء المتداخل باستخدام موفر InMemory؛ نجح الاختبار المقابل على SQL Server.

لتشغيل اختبارات التكامل، يحدد `RETAL_TEST_SQLSERVER` اتصال خادم اختبارات مخصص. ينشئ كل اختبار قاعدة مستقلة ويحذفها بعد الانتهاء.
